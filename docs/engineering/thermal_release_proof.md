# Thermal release proof

The v1R [thermal model definition](../../simulations/thermal/slate-pocket-v1r/model/model.yaml) is a plan. It has no released geometry, complete material properties, boundary characterization, solver run, or measured correlation. The [thermal auditor](../../buildslate/thermal_proof.py) checks a future design package without promoting this plan to release evidence.

## Release package

Store `thermal-release.json`, `solver-input.json`, and `solver-results.csv` in `engineering/hardware/released/thermal/`. The `thermal_release` record in [hardware readiness](../../engineering/hardware/readiness.yaml) must name the release JSON with its SHA-256, revision, reviewer, and approved disposition. The JSON must use schema version 1 and identify v1R. It names the actual solver and version and binds the exact solver input and result bytes.

The release also binds the selected BOM, routed PCB, [mechanical STEP assembly and manifest](mechanical_release_proof.md), and [power safety release](power_safety_proof.md) by SHA-256. The readiness gate checks those hashes against approved upstream records and requires a passing part proof. The solver input repeats the mechanical assembly and power design hashes, so a revised enclosure, board, battery, or charge limit invalidates the thermal package. The battery and compute temperature limits come from the released selected parts, not from a generic default.

## Solver input checks

The solver input lists density, heat capacity, and directional conductivity for the enclosure, display, battery, vapor chamber, graphite, and phase-change material. It gives bondline and thermal resistance for the SoC/TIM, TIM/spreader, spreader/frame, battery/structure, and rear-cover interfaces. Each property group needs a hash-bound source file under `engineering/hardware/released/thermal/sources/` or `engineering/hardware/released/parts/`. Planning Markdown, YAML, and JSON cannot be used as property evidence. The mechanical manifest must contain the named thermal roles.

The input defines distinct boundaries for 25 °C open air, 35 °C open air, handheld contact, and 25 °C charging. Every boundary has convection and emissivity values with source evidence; the handheld boundary also needs contact area and conductance. Each case must reference its designated boundary. Medium and fine mesh cell counts must differ by at least 50 percent.

The required cases mirror the [thermal test matrix](../../simulations/thermal/slate-pocket-v1r/test-matrix.yaml): sustained AI at 25 °C and 35 °C, a 60-second peak burst, a handheld sustained ramp, and wired charging at idle. Each case maps every power-release load to heat deposits in expected mechanical roles and separates heat from exported energy. Camera heat must cover front and rear modules. Exported energy requires its own source evidence. Noncharging cases cover the full declared sustained or peak electrical loads. The charging case is limited to the power release's idle-system draw, locates charger heat on the board, and calculates it from the declared charge-path loss. Every case also includes pack heat calculated as current squared times source-backed internal resistance. This prevents the thermal model from silently omitting memory, storage, radios, display, charger, or pack losses.

## Result checks and limits

The result CSV has one medium and one fine row per case, with ambient, simulated duration, input and outbound heat, and maximum skin, battery, and junction temperatures. Both peak-burst rows must cover at least 60 seconds; steady cases use a zero-duration solution. The auditor compares input heat with the solver input, requires nonnegative heat and temperatures no lower than ambient, and rejects a medium-to-fine maximum-temperature change above 1 °C. For steady cases it rejects an energy imbalance above 3 percent. It compares maximum skin against the 43 °C v1R profile limit, battery against the selected pack's operating limit or charge-temperature limit, and junction against the selected compute rating. The burst is treated as transient, so the steady-state outbound-heat check does not apply there.

Run `python -m buildslate.thermal_proof --repo-root .` to inspect the controlled package. The [synthetic fault fixture](../../validation/validate_thermal_proof.py) exercises release, source, heat-map, boundary, mesh, energy, and temperature failures. Passing these checks means the reviewed model and tabulated results are internally consistent with the recorded inputs. They do not establish solver fidelity, complete temperature coverage, material accuracy, firmware throttling, user comfort, or safe operation. The [correlation plan](../../simulations/thermal/slate-pocket-v1r/correlation-plan.md) and serialized EVT0 measurements remain required before using predictions for design signoff.
